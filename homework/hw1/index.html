Public-Key Cryptography: From Private Key to Public Key in Ethereum

10/10/2026

The idea

Every Ethereum account starts from a secret random number, the private key. From it we compute the public key, which can be shared with everyone. The computation only works in one direction: getting the public key from the private key takes a fraction of a second, but once the public key is known there is no practical way to go back and recover the private key. This is why the public key can be published without putting the account at risk.

In Ethereum the public key is obtained from the private key with elliptic-curve scalar multiplication. An elliptic curve over the integers modulo a prime $p$ is the set of points $(x, y)$ with

$$y^2 \equiv x^3 + ax + b \pmod p$$

plus a point at infinity $\mathcal{O}$. Two points $P$ and $Q$ can be added: take the line through them (the tangent if $P = Q$), find the third point where it meets the curve and reflect it over the x axis. With slope $\lambda$ the formulas are

$$\lambda = \begin{cases} \dfrac{y_2 - y_1}{x_2 - x_1} & P \ne Q \\[2mm] \dfrac{3x_1^2 + a}{2y_1} & P = Q \end{cases} \qquad x_3 = \lambda^2 - x_1 - x_2, \qquad y_3 = \lambda(x_1 - x_3) - y_1$$

where every division is a multiplication by a modular inverse. Adding a base point $G$ to itself $k$ times gives the public key

$$Q = kG = \underbrace{G + G + \dots + G}_{k \text{ times}}$$

Computing $Q$ from $k$ is fast; recovering $k$ from $Q$ is the Elliptic Curve Discrete Logarithm Problem, which is infeasible on the real curve secp256k1. That is what makes it a one-way function. The program below uses the toy curve $y^2 = x^3 + 7 \pmod{17}$, which has the same equation as secp256k1 but only 17 points, with $G = (1, 5)$ and private key $k = 6$.

Generate the toy public key

The program prints $G, 2G, \dots, kG$ by repeated addition, then computes the same result with double-and-add, the faster method for large $k$: it reads the bits of $k$, doubles at every bit and adds $G$ when the bit is 1.

Slowed-down visualisation

Over $\mathbb{F}_{17}$ the curve is a set of grid points and a "line" wraps around the grid. Each operation is shown in four phases: the operands, the line, the third intersection $-R$ and its reflection $R$. Press Play, or Step to go one phase at a time.

Statistical exploration

On the toy curve every private key can be tried, so the results are exact. Choose a base point: its order decides how many private keys exist, and everything below is computed over all of them.

Distribution of x and y, frequency of individual values

x is far from uniform: only the 9 values for which $x^3 + 7$ is a square modulo 17 can appear, each twice, as $(x, y)$ and $(x, -y)$. With $G = (1, 5)$ only 4 values appear. With a generator of order 18 instead, every y appears exactly once.

Apparent uniformity

Every key gives a different point: $k \mapsto kG$ is a bijection, so a uniform private key gives an exactly uniform public key. Only the single coordinates look non-uniform.

Distribution of bits

Coordinates go from 0 to 16, so the most significant bit (x4, y4) is 1 only for the value 16 and is almost always 0. The other bits are not balanced either, because only a few values appear. On secp256k1, where $p$ is very close to $2^{256}$, this bias disappears.

Correlation and avalanche

For $G = (1, 5)$ the Pearson correlation between $k$ and $x$ is 0, but the table below shows the mirror symmetry $x(k) = x(9 - k)$, because $(9 - k)G = -kG$: Pearson only sees linear dependence. Avalanche is the share of the 10 output bits that change when one bit of $k$ is flipped; it is close to 50%, but with so few bits it means little.

One-way function or hash function?

PropertyElliptic-curve one-way functionCryptographic hash function
Hard to invertEssential (ECDLP)Essential
Uniform outputEssential, exact (bijection)Required
Uniform coordinates and bitsNot requiredRequired
No correlation, avalancheNot design goalsDesign criteria
No algebraic structureThe opposite: $(a + b)G = aG + bG$ is needed for signaturesEssential

The meaningful property for the one-way function is that it is hard to invert, which no statistic can measure. Uniform bits, no correlation and avalanche are properties of hash functions: the toy curve fails them, and it does not need them.

Conclusion

The program shows the forward direction of the one-way function: from $k = 6$ and $G = (1, 5)$ we get the toy public key $Q = (5, 8)$, and double-and-add reaches it in about $\log_2 k$ operations instead of $k - 1$. The statistics split the properties into two groups:

  • What matters for the one-way function holds. Every private key gives a different point, so a random key gives a perfectly uniform public key, with no key more likely than another.
  • What matters for a hash function does not. Coordinates and bits are biased, the zero correlation hides the mirror symmetry, and the structure $(a + b)G = aG + bG$ links the outputs of related inputs. The curve does not need these properties: signatures rely on exactly that structure.
  • Hardness cannot be measured. On the toy curve $k$ is found by trying 8 values. The one-way property only holds at the size of secp256k1, about $2^{256}$ points, and no statistical test can show it.

Ethereum uses both tools: the public key comes from the curve, and the address is a Keccak-256 hash of it, which adds the uniformity and avalanche that a curve point lacks.
