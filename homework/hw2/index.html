From Wallet Seed to Ethereum Address: Hashing, Key Derivation and Cryptographic Primitives

13/10/2026

The idea

A wallet such as MetaMask or Rabby asks you to write down 12 words once. From those words it can rebuild every private key and address of every account, on any device. The 12 words are turned into an address by a chain of standards, each solving a different problem:

Mnemonic12 words
BIP-39
Seed64 bytes
BIP-32 / 44
Private key32 bytes
secp256k1
Public key64 bytes
Keccak-256
Address20 bytes

Along the way five different kinds of operation appear, and it helps to keep them apart:

KindWhat it doesIn the pipeline
Key generationCreates new secret randomness; not reproducible128 random bits behind the mnemonic
Key derivationComputes keys deterministically from a secret: same input, same keysBIP-39 seed, BIP-32 / BIP-44 child keys
Public-key cryptographyLinks a private and a public key; enables signaturessecp256k1
HashingMaps any input to a fixed-size digest with no visible structureKeccak-256 (and SHA-256 / SHA-512 inside BIP-39 and BIP-32)
ChecksumDetects accidental errors; it is not a protection against attackersLast BIP-39 word, EIP-55 capital letters
EncodingChanges the representation, adds no secrecyWords, hexadecimal, mixed case

From mnemonic to address

My implementation of the whole pipeline. The default phrase is the standard test mnemonic: its first address, 0x9858EfFD…Eda94, is the one a wallet like MetaMask shows when you import the same words. Change the account number to get the next addresses of the same wallet, or add a passphrase to get a completely different wallet.

Historical context

  1. 1977RSA — the first practical public-key cryptosystem.
  2. 2001SHA-2 (SHA-256, SHA-512) — standardized by NIST; used inside BIP-39 and BIP-32.
  3. 2012BIP-32 — hierarchical deterministic wallets: a tree of keys from one seed.
  4. 2013BIP-39 — the seed written as a mnemonic sentence.
  5. 2014BIP-44 — a standard path in the tree for each coin and account.
  6. 2015SHA-3 — standardized by NIST (FIPS 202), based on Keccak.
  7. 2016EIP-55 — checksum hidden in the capital letters of Ethereum addresses.

SHA-2 and Keccak / SHA-3 are both cryptographic hash functions, but with different designs: SHA-2 is built like its predecessors (Merkle–Damgård), Keccak is a sponge and won the SHA-3 competition in 2012. Ethereum adopted Keccak before NIST finished the standard, and NIST then changed the padding (domain separation), so Keccak-256 ≠ SHA3-256: same permutation, different output.

Statistical properties

Each experiment uses fresh random inputs, so the numbers change slightly at every run.

Keccak-256 behaves like a random function

Flipping one input bit changes about half of the 256 output bits, and the counts follow the binomial distribution expected from independent fair coins. This is what makes the address unrelated to the public key it comes from, unlike secp256k1, which keeps the algebraic structure.

EIP-55: how strong is the checksum?

Only the letters a–f carry checksum bits, and each is uppercase with probability ½ because it copies one bit of a hash. An address has on average 15 letters, so a mistyped address passes the check with probability about $(13/16)^{40} \approx 1/4000$: good against typos, useless against an attacker, who can simply compute the right capitals.

BIP-39: the checksum word

12 words carry 132 bits: 128 of entropy and 4 of checksum, so a random sequence of 12 words is a valid mnemonic with probability 1/16. If one word is replaced by another word of the list, the wallet notices in 15 cases out of 16.

Conclusion: why so many techniques?

Following the pipeline step by step shows that a wallet is not one algorithm but a chain of small, independent tools. The only real secret is the 128 bits of entropy created at the start: everything after it is computed deterministically, so the same 12 words always give the same keys and addresses, in my implementation as in any standard wallet. No single algorithm could do every job, because the jobs require opposite properties:

  • BIP-39 / BIP-32 / BIP-44 — key management and derivation. One backup that a person can write on paper must produce many keys, in the same way on every wallet. BIP-39 turns the entropy into words people can copy and into a seed, using PBKDF2 with 2048 rounds to make guessing passphrases slower. BIP-32 grows a whole tree of keys from that seed, and BIP-44 fixes where Ethereum accounts live in the tree (m/44'/60'/0'/0/i), so that different wallets find the same addresses. The hardened steps (') make sure that a leaked child key does not expose the keys above it.
  • secp256k1 — the public/private key relationship and signatures. Here we need a one-way function with algebraic structure: the owner of the private key can sign a transaction and anyone can verify the signature with the public key, without learning the private key. As seen in Homework 1, this structure is exactly what a hash function must not have.
  • Keccak-256 — hashing. It needs the opposite: no structure at all, uniform output and avalanche. It shortens the 64-byte public key to a 20-byte address and makes the address unrelated to the key, so nothing about the key can be read from it.
  • EIP-55 — checksum and error detection. A cheap way to catch typos when an address is copied by hand, hidden in the capital letters so that old lowercase addresses remain valid. It adds no security against an attacker, who can always compute the correct capitals.

Keeping the roles separate also makes the system easier to change: Bitcoin wallets use the same BIP-39 words and the same BIP-32 tree, but a different BIP-44 path and different hashes for the address, so one mnemonic can safely hold both Bitcoin and Ethereum accounts.

The statistics confirm this division of work. Keccak-256 output is indistinguishable from random bits: about 128 of 256 bits change when one input bit is flipped, following the Binomial(256, ½) distribution, and ones and zeros are balanced. The two checksums, instead, are designed to catch accidents and nothing more: a wrong word passes the BIP-39 check in 1 case out of 16, and a mistyped address passes the EIP-55 check in about 1 case out of 4000. Security comes from the 128 random bits of entropy and from the hardness of the discrete logarithm on secp256k1; hashing, checksums and encodings make the keys usable, comparable and hard to mistype.
